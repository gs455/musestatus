# Changelog

## v1.2.0 — 2026-10-28

- Burger menu: the separate Changelog and Code history entries combine into one "Code History / CL" button (model: /artifacts) that opens the code-history page. The code-history page carries a Changelog button in its docs bar, and the changelog page keeps its Brief/Full presentation and links back — the pair stays cross-linked from one entry point. The shortcut tasks collapse to match: one "Code History / CL" task on stock H opens the combined page, and L is unassigned by default. Saved maps migrate once (`historyStockMigrated` in the synced state): an L/H pair still at the old stock values drops the L entry; a key customized on either task is left untouched.
- New burger item "How to use": a popup on the Shortcuts pattern with a succinct guide to the page (what it is, Starred and the file browser, edit mode, refreshes, the green v1.1.0 panes), editable in place — Edit → textarea → Save / Revert to stock — persisted as `howToUseText` in the synced view state ("" = stock), mirroring /artifacts. Its Shortcuts task ("How to use") starts unassigned.
- New shortcut task "Burger menu (at cursor)" on stock V: V opens the burger menu at the last known mouse position (tracked on mousemove; the normal burger anchor when none is known) and V again closes it; Esc closes it as usual. Bare Ctrl still toggles the menu at its normal anchor. All other stock keys are unchanged, and there is still no autofit task — A remains expand/collapse all only.
- Code-history generator fix: the version-body regex in `scripts/build-code-history.mjs` ended its lazy capture at the first `\s*$` lookahead, so every version's changelog bullets silently rendered empty in code-history.html since v1.1.0. The capture now ends at the next version header or end of file, and the bullets appear above each release's commits as the generator always intended.

## v1.0.0 — 2026-10-23

- Publish route dispatched before the hub gate (it carries its own Bearer key; the VM publisher never has the hub proxy key).
- Data layer migrated KV → D1 the same night: the first KV publish wrote ~958 keys and nearly exhausted the account's daily free-tier KV write cap (961 of 1,000 account-wide). Sections, fs rows, preference bodies and view state now live in `musestatus_*` tables (D1 database anvari-hub — the VM API token cannot create D1 databases, 401 code 10000; worker creates its tables on first use). The publisher contract is unchanged; rows are written only on change. The musestatus-data KV namespace is retired in place (no further writes; binding removed).
- Write discipline hardened (owner's fix spec): every D1 row carries a sha256 hash; the publisher sends hashes with all items and the worker writes only rows whose hash differs — a no-change publish writes zero rows. The fs tree ships as hash-bucket chunk blobs (bucket = sha256(path) mod 48; 48 rows for the full 22.6k-folder tree), never per-folder rows — bucket membership is stable, so a typical run rewrites only the buckets that changed (an earlier sorted-chunk design cascaded on insertions and was replaced the same night). Chunk hashes cover folder content only (publish stamps excluded), and the publisher's own state files are excluded from the published tree so runs don't churn themselves.

- First release of musestatus at armanai.pages.dev/musestatus/: 12 data-driven panes (Starred & pinned, File system, Preferences, Machines, Connectors, Usage & billing, Automations, Skills, Tools, Assistants & chats, Artifacts & hub, Memory), hub-gated worker with KV view-state sync and a publish endpoint for the VM publisher, claudestatus-style chrome with movable panes, editable tables, edit mode and spacing sliders.
